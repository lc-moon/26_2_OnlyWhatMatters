# 실습일지 만들기

## 먼저 알 것 — 재료는 날짜 범위로 고른다

일지 번호와 작업 주차는 한 칸 어긋난다. 마감이 월요일 수업일이고 실습일자가
"직전 마감 다음 날 ~ 이번 마감일"이라, 7주차 일지에는 6주차 작업이 주로 들어간다.
**재료는 주차 번호가 아니라 `docs/실습일지/README.md`의 실습일자 범위로 고른다.**

## 절차

### 1. 대상 일지와 실습일자를 정한다

- 인자가 있으면(`6주차`, `6`) 그 일지
- 없으면 README 일정표에서 **제출 칸이 비어 있고 마감이 가장 가까운** 일지
- README에서 그 일지의 실습일자 범위(예: `2026. 10. 13. ~ 2026. 10. 19.`)를 읽어 시작일·끝일로 쓴다
- 이미 `NN주차.md`가 있고 제출 표시가 돼 있으면 고치지 않는다. 사용자에게 알리고 멈춘다

### 2. 그 날짜 범위의 재료를 모은다

```bash
ls docs/기록/                                              # 파일명 날짜가 범위 안인 것
git log --since="YYYY-MM-DD 00:00" --until="YYYY-MM-DD 23:59" --stat
git log --since=... --until=... -p -- docs/현황.md         # 현황이 어떻게 바뀌었나
```

- **기록** (`docs/기록/`): 범위 안의 파일 전부. `요약`, `확인한 것`, `캡처 후보` 절이 핵심 재료다
- **decisions** (`docs/decisions.md`): 날짜가 범위 안인 항목
- **커밋**: 기록에서 빠진 작업이 있는지 확인하는 용도. 코드 발췌 위치를 찾는 데도 쓴다
- **현황.md 변화**: 검증된 사실이 새로 생겼는지, 남은 작업이 어떻게 바뀌었는지

**재료가 비어 있거나 부족하면 지어내지 말고 사용자에게 묻는다.**
"이 기간에 기록과 커밋이 없습니다. 무엇을 하셨나요?"
기록 체계가 생기기 전 기간(6주차 일지의 9/29~10/7 등)은 특히 그렇다.

### 3. 원고 `docs/실습일지/NN주차.md`를 쓴다

`NN`은 두 자리(`06주차.md`, `12주차.md`). 문체는 개조식("~ 구현", "~로 변경", "~함").

```markdown
# NN주차 실습일지

> 실습일자: 2026. M. D. ~ 2026. M. D. / 마감 M/D
> 재료: 기록 [YYYY-MM-DD_제목](../기록/...), decisions D-NNN, 커밋 N건

## 실습내용
- 불릿 3~6개. 한 주간 수행한 내용을 간략하게

## 실습결과

### 1. 항목 제목
- 무엇을 했나 (1~3줄)
- 실행 결과·수치 → [캡처 1: 설명]
- 주요 소스코드 (`파일:줄`)
  ```python
  # 30줄 이내 발췌
  ```

### 2. 바뀐 판단 — (decisions 항목이 있을 때만)
- 기존: 원래 하려던 것
- 문제: 부딪힌 문제 (수치)
- 변경과 이유: 무엇으로 바꿨고 왜

## 기타
- 향후 해야 할 사항 (현황.md 남은 작업 + 다음 일지 기간의 일정)

## 캡처 목록
| 번호 | 무엇 | 띄우는 명령 |
|---|---|---|
| 1 | | |
```

- **실습내용**: 불릿 3~6개. 기록의 `요약`을 바탕으로 하되 그대로 옮기지 말고 일지 단위로 묶는다
- **실습결과**: 항목마다 *무엇을 했나 + 실행 결과·수치 + 주요 소스코드 발췌*.
  - 코드 발췌는 `파일:줄`을 밝히고 **30줄 이내**. 핵심 로직만 고른다
  - 그 기간 decisions 항목이 있으면 **"기존 → 문제 → 변경과 이유"**로 쓴다. 1학기 6주차 일지의 집계 로직·점수 공식 변경이 좋은 예다
- **기타**: `현황.md` 남은 작업과, 다음 일지 기간에 `프로젝트.md` 일정상 할 일
- **캡처 목록**: 넣을 화면마다 무엇을, 어떤 명령으로 띄우는지. 기록의 `캡처 후보`에서 가져온다.
  명령을 모르면 비워 두지 말고 사용자에게 묻는다

### 4. 원고를 사용자에게 보여주고 고친다

원고 전문을 보여주고 확인받는다. 고칠 점을 반영해 다시 보여준다. **확정 전에는 docx를 만들지 않는다.**

### 5. 확정되면 docx를 만든다

`anthropic-skills:docx` 스킬로 `docs/실습일지/양식.docx`를 복사해 채우고
`docs/실습일지/실습일지_NN주차.docx`로 저장한다. 양식 원본은 건드리지 않는다.

- 표의 다섯 칸(주제 / 실습일자 / 실습내용 / 실습결과 / 기타)에 원고를 옮긴다.
  각 칸의 안내 문구("- 한 주간 수행한 내용을 간략하게 기술" 등, 빨간 글씨)는 첫 줄에 그대로 두고,
  본문은 그 아래 빈 단락의 서식(검은 글씨)을 복제해 쓴다
- 소스코드는 **고정폭 글꼴**(예: Consolas)로
- 캡처 자리는 `[캡처 N: 설명]` 문단으로 표시해 사용자가 직접 붙여 넣게 한다
- 캡처 목록은 docx에 넣지 않는다(원고에만 둔다)

`양식.docx`는 학번·이름이 들어 있어 git에서 제외된다. 파일이 없으면 사용자에게 알리고 멈춘다.

### 6. README에 작성 완료를 표시한다

`docs/실습일지/README.md` 일정표의 `작성` 칸에 표시한다(예: `✔ 10/8`).
`제출` 칸은 사용자가 냈다고 말했을 때만 표시한다.

## 규칙

- **기록·커밋에 없는 일을 지어내지 않는다.** 재료가 비면 그 기간에 무엇을 했는지 사용자에게 묻는다
- 분량을 늘리려고 커밋 메시지를 옮겨 적지 않는다
- 수치는 기록·현황에 적힌 것만 쓴다. 추정치는 추정이라고 밝힌다
- 제출한 일지의 원고(`NN주차.md`)는 고치지 않는다. 틀린 것이 있으면 다음 일지에서 정정한다
