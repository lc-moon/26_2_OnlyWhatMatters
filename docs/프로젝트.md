## 1. 한 줄 설명

GitHub 저장소를 연결하면 사용 중인 오픈소스 라이브러리의 알려진 취약점을 추적하고,
**내 코드가 그 취약한 함수를 실제로 호출하는지**까지 판별해 "지금 당장 고쳐야 하는 것"만 선별해 알려준다.

2026년 2학기 심화응용프로젝트 개인 프로젝트. 개발자는 컴퓨터시스템공학과 3학년 1인.

## 2. 왜 만드는가

기존 도구(GitHub Dependabot 등)는 **설치된 버전만 보고** 경고를 만든다.
실제로는 위험하지 않은 경고가 쌓여 정작 무엇이 급한지 알기 어렵다(알림 피로).
수요층은 보안 인력이 따로 없는 소규모 팀, 스타트업, 개인 개발자다.

상용 솔루션(Semgrep Supply Chain, Endor Labs, Snyk)은 도달 가능성 분석, 즉 "취약 함수를 실제로 부르는가"를 이미 제공한다.
다만 **"어떤 함수가 취약한지"는 보안 연구 인력이 수작업으로 규칙화**한다.

이 프로젝트의 차별점은 **그 해석을 LLM으로 자동화하고, 정확도를 정량 평가하는 것**이다.
(차별점을 이렇게 다시 잡은 경위: `decisions.md` D-001)

## 3. 데이터 구조 배경

| 이름 | 무엇인가 | 구조화 정도 |
|---|---|---|
| **CVE** | 보안 결함 하나에 붙는 전 세계 공통 번호 | 내용은 대부분 줄글 |
| **OSV** | CVE 등을 "PyPI의 sqlparse, 0.4.2 미만 영향"처럼 필드로 재정리한 공개 DB + API | `affected.ranges`(버전), `severity`, `references`(FIX 커밋 링크)는 구조화됨 |

**어떤 함수가 취약한지는 OSV에도 구조화된 필드가 없다.** PyPI 덤프에서 함수명을 구조화 필드
(`ecosystem_specific.imports`)에 넣은 항목은 26,126건 중 2건뿐이었다(2026-10-08 실측, `현황.md` §2).
`details` 줄글 안에만 있고, 문서 표기와 실제 호출 경로가 다른 경우도 있다.
예: 문서는 `sqlformat.format`, 사용자는 `sqlparse.format`으로 호출.

**이 간극이 LLM을 쓰는 유일한 이유다.** 버전 판정처럼 구조화된 필드로 되는 일은 전부 코드가 한다.

**수정 커밋은 세 곳에서 찾는다**: `references`의 `FIX` 링크, `affected[].ranges`(GIT)의 `fixed`,
그리고 `FIX`가 아닌 타입(주로 `WEB`)으로 붙은 GitHub 커밋 링크. GHSA는 커밋 링크를 전부 `WEB`으로 붙이기 때문이다(D-003).

덤프에는 악성 패키지(`MAL-`)와 철회 항목(`withdrawn`)이 섞여 있고, 같은 취약점이 여러 ID로 중복된다.
분석 전에 빼고 `aliases`로 묶는다.

## 4. 동작 방식

```
1. 의존성 목록(패키지·버전) 추출          코드
2. OSV 버전 범위와 대조 → 취약 버전 판정   코드 (packaging)   ← 여기까지가 Dependabot 수준
3. 설명문 + 수정 커밋 diff → 취약 함수     LLM  (JSON 추출, 취약점 1건당 1회, 캐싱)
   → 그 함수가 실제 패키지에 있는지 재검증  코드 (환각 차단)
4. 내 코드가 그 함수를 호출하는가          코드 (ast, 실행하지 않음)
5. 즉시 조치 / 여유 있음 / 판단 불가 분류   코드
   → 결과 설명문                          LLM  (판정은 바꾸지 않음)
```

- **OSV 사용 방식 두 가지**: 저장소를 처음 연결할 때는 API로 조회한다.
  "새 취약점이 뜨면 영향받는 저장소를 거꾸로 찾는" 기능을 위해서는 전체 데이터를 DB에 넣고 매일 동기화한다.
  API만으로는 이런 역방향 조회가 안 된다
- **캐시 단위는 취약점 하나**: 같은 패키지라도 다른 취약점이면 새로 1회 호출한다.
  처음 보는 취약점은 그 자리에서 LLM을 불러야 하므로 응답이 늦어진다(기획 단계 추정 건당 5~10초, 미측정).
  그래서 버전 대조 결과를 먼저 보여주고 함수 분석이 끝나는 대로 등급을 갱신한다
- **사용자 흐름**: GitHub 로그인 → GitHub App 설치(저장소 선택) → 분석 요청(작업 큐, 백그라운드) → 대시보드 표시
- **소스 수집 범위**: 저장소 전체 클론 대신 의존성 파일과 `.py` 파일만 가져온다

### 범위 — 밀리면 무엇을 빼는가

여유 주가 없다. 일정이 밀리면 **여유 시** 항목부터 뺀다.

| 구분 | 항목 |
|---|---|
| **필수** (지킨다) | 의존성 추출 / OSV 대조 / LLM 함수 추출 / ast 호출 판정 / 결과 화면 / 정확도 평가 |
| 여유 시 (먼저 뺀다) | 웹훅 자동 재분석 / GitHub 이슈 알림 / 타 언어 지원 / CI 실행 모드 |

CLI부터 만들고 GitHub 연동과 웹은 그다음이다. 이 순서면 일정이 밀려도 동작하는 결과물이 항상 남는다.

## 7. 평가 방법

정확도 평가는 부가 기능이 아니라 핵심 산출물이다. 12주차에 웹보다 먼저 한다.

**정답표를 붙인 테스트 저장소로 판정 정확도를 잰다.**

| 테스트 케이스 | 정답 |
|---|---|
| 취약 버전 + 해당 함수 호출 | 즉시 조치 |
| 취약 버전 + 해당 함수 미사용 | 여유 있음 |
| 패치된 버전 | 알림 없음 |
| 동적 호출 등 애매한 경우 | 판단 불가 |

추가로 볼 것:
- **LLM 함수 추출 정확도**: 사람이 확인한 정답(`eval/candidates.csv` 20건부터, 작성 규칙과 채점 방식은 `eval/README.md`)과 비교
- **판단 불가 비율**: ast 분석은 예외가 많으므로 완벽 대신 이 비율을 관리 지표로 삼는다
- **캐시 효과**: 캐시 미적중과 적중 시의 분석 소요 시간
- **과거 재생 시연**: 취약점 데이터를 과거 시점으로 잘라 "이날 이 알림이 갔을 것"을 보여준다

목표 형태는 "기존 방식 대비 경고 수 N% 감소, 실제 위험 누락 0건". 구체 지표와 정답 데이터 규모는 12주차 전에 확정한다.

정답 데이터는 `eval/`에 두며 **사람이 채운다.** 스크립트가 덮어쓰거나 추측으로 채우지 않는다.
