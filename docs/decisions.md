## D-003 · 수정 커밋 근거를 FIX 링크에서 "WEB 타입 GitHub 커밋"까지 넓힘

- 날짜: 2026-10-08 / 6주차
- 근거 기록: [기록/2026-10-08_저장소세팅과OSV사전검증](기록/2026-10-08_저장소세팅과OSV사전검증.md)

**원래 계획**
LLM 입력이 될 수정 커밋은 OSV `references`의 `FIX` 링크와 `affected[].ranges`(GIT)의 `fixed` 이벤트에서만 가져온다.
측정 전에 정한 기준: 최근 2년 고유 취약점 중 분석 가능 후보가 25% 미만이면 범위 조정(`현황.md`).

**부딪힌 문제**
- 이 정의로는 최근 2년 후보가 **10.8%**(3,278건 중 355건)였다. 기준상 "범위 조정"
- 원인은 표기 방식이었다. **GHSA는 커밋 링크를 전부 `WEB` 타입으로 붙이고**(5,260건), `FIX`를 쓰는 곳은 PYSEC뿐이다(2,163건)
- WEB 타입 GitHub 커밋까지 넣으면 후보는 **53.3%**였다. 두 기준의 판정이 갈렸다
- WEB 커밋이 실제 수정 커밋인지 확인했다. FIX(또는 GIT fixed)와 WEB 커밋이 함께 있는 묶음 1,241건 중
  **99.8%에서 WEB 커밋이 수정 커밋과 일치**했고, **93.0%는 WEB 커밋 전부가 수정 커밋**이었다
- 후보 표본 10건(9건이 WEB 출처)의 diff를 실제로 받아보니 10건 모두 성공했고, 모두 `.py` 변경을 포함했다

**검토한 선택지**
1. 원안 유지(FIX + GIT만) — 근거가 확실함 / 최근 2년의 약 11%만 정밀 판정. 차별점(D-001)이 소수에만 적용된다
2. WEB 타입 GitHub 커밋까지 근거로 인정 — 후보 약 53% / 수정 커밋이 아닌 커밋이 섞일 수 있다(위 대조에서 약 7%의 묶음에 수정 커밋 목록에 없는 WEB 커밋도 있었음. 다른 브랜치로 옮긴 백포트일 수도 있어 전부 오류라고 단정하지는 못함)
3. details만으로 추출 — 커버리지 최대 / diff 교차 확인이 없어 "판단 불가"가 "여유 있음"으로 바뀔 위험. 위험 누락 0 원칙과 충돌

**결정과 이유**
2번. WEB 타입은 "수정 커밋이 아니다"가 아니라 GHSA의 표기 방식이었고, 일치율이 이를 뒷받침한다.
측정 전 기준은 바꾸지 않았다. 공식 판정은 "범위 조정"이고, 이 결정이 그 조정 내용이다.
근거가 없는 나머지는 원안대로 "판단 불가 + 업데이트 권장"으로 둔다. 정답 후보(`eval/candidates.csv`)도 이 풀에서 뽑았다.

**남은 한계**
- 일치율은 PYSEC가 FIX를 달아준 묶음에서 잰 것이다. **WEB 커밋만 있는 묶음에서도 같은지는 미확인**이다
  → 7주차 정답 작성 때 WEB 출처 18건이 실제 수정 커밋인지 note에 남겨 확인한다
- 한 묶음에 WEB 커밋이 여러 개면 수정 커밋이 아닌 것이 섞일 수 있다. LLM에 넘기기 전에 코드로 거르는 단계가 필요하다
  (방법은 9주차 설계 때 정한다)

## D-002 · LLM API 키를 사용자에게 받지 않고 서비스가 부담

- 날짜: 기획 단계 (1~5주차, 정확한 날짜 미상)
- 근거 기록: 노션 [캡스톤 프로젝트 주제](https://app.notion.com/p/3e34a3212e4f81e9b7a2f1ccc7703afa) §4 "LLM 캐시 구조와 응답 속도" (페이지 최종 수정 2026-09-28)

**원래 계획**
비용 부담을 줄이려고 사용자가 자기 API 키를 등록하는 방식을 고려했다.

**부딪힌 문제**
- 사용자별 키를 쓰면 해석 결과를 공유 캐시로 재사용할 수 없다. 같은 취약점을 사용자 수만큼 중복 분석하게 된다
- 소규모 팀이 대상인데 키 발급을 요구하면 진입 장벽이 크다

**검토한 선택지**
1. 사용자 키 필수 — 서비스 비용 0 / 캐시 공유 불가, 진입 장벽
2. 서비스 키 + 공유 캐시 — 비용이 취약점 수에 비례, 진입 장벽 없음 / 서비스가 비용을 부담하고 악용 대비가 필요
3. 혼합 — 선택권은 넓음 / 캐시 공유 규칙이 복잡해지고 1의 단점이 일부 남음

**결정과 이유**
2번. 취약점 1건당 1회로 제한해 캐싱하면 비용이 사용자 수가 아니라 취약점 수에 비례한다.
신규 취약점이 하루 수 건 수준인 Python 생태계라면 개인이 감당 가능한 규모다.
단 **"하루 수 건"은 아직 실측 전**이다. OSV 사전 검증에서 확인되면 `현황.md`에 적는다.

**남은 한계**
- 악용 시 비용이 발생한다 → 사용자당 일일 분석 횟수 제한이 필요
- CI 실행 모드(여유 시 항목)에서도 서버 캐시를 조회하는 방식으로 같은 이점을 유지할 계획

## D-001 · 차별점을 "도달 가능성 분석"에서 "LLM 기반 취약 함수 해석 자동화"로 변경

- 날짜: 기획 단계 (1~5주차, 정확한 날짜 미상)
- 근거 기록: 노션 [캡스톤 프로젝트 주제](https://app.notion.com/p/3e34a3212e4f81e9b7a2f1ccc7703afa) §5 "기존 도구와의 차이" (페이지 최종 수정 2026-09-28)

**원래 계획**
내 코드가 취약 함수를 실제로 호출하는지 판별하는 것(도달 가능성 분석)을 핵심 차별점으로 삼았다.

**부딪힌 문제**
Semgrep Supply Chain, Endor Labs, Snyk 같은 상용 솔루션이 이미 이 기능을 핵심으로 제공한다.
Python 전용 오픈소스 도구도 있다.

**검토한 선택지**
1. 주제 변경 — 겹침을 피함 / 기획을 처음부터 다시 해야 함
2. 그대로 가되 무료·한국어를 차별점으로 — 작업 변경 없음 / 기술적 기여가 아니라 포장의 차이
3. 상용 도구가 인력으로 처리하는 부분을 자동화 — 기술적 기여가 분명함 / 정확도를 스스로 입증해야 함

**결정과 이유**
3번. 상용 솔루션은 "어떤 함수가 취약한지"를 보안 연구팀이 수작업으로 규칙화한다.
이 해석을 LLM으로 자동화하고 정확도를 정량 평가하는 것은 학부 범위에서 실현 가능하고 기술적 기여가 분명하다.

**남은 한계**
상용 대비 정확도·커버리지는 낮을 수밖에 없다. 평가로 그 격차를 수치화하는 것이 목표다.
