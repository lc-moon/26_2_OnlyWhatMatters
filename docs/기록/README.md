## 흐름 요약

**1~5주차 — 기획·설계**
기록 체계를 만들기 전이라 날짜별 기록이 없다. 주제 선정, OSV 구조 조사, 기존 솔루션 조사, 아키텍처 설계를 했다.
내용은 노션 [캡스톤 프로젝트 주제](https://app.notion.com/p/3e34a3212e4f81e9b7a2f1ccc7703afa), 그 과정의 결정은 `decisions.md` D-001·D-002.

**6주차 — 전제를 데이터로 확인하다**
저장소를 만들고 문서 체계부터 세웠다. 바뀌는 상태와 규칙을 나누고, 매일 기록이 실습일지로 이어지게 했다.

이어서 계획 전체가 기대는 전제 — LLM이 읽을 수정 커밋이 충분히 있는가 — 를 OSV PyPI 덤프로 쟀다.
결과에 기준을 맞추지 않으려고 판정 기준을 먼저 적어 두었고, 그 기준으로는 10.8%라 "범위 조정"이 나왔다.
원인을 따라가 보니 수정 커밋이 없는 게 아니라 GHSA가 수정 커밋을 다른 타입(WEB)으로 붙이고 있었다.
대조로 그 커밋들이 실제 수정 커밋임을 확인하고 근거 출처를 넓혀 후보를 53%로 조정했다(D-003).
함수 정보가 구조화 필드에 사실상 없다는 것도 확인해, LLM을 쓰는 이유가 데이터로 뒷받침됐다.
