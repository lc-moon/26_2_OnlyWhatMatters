# 2026-10-08 · 저장소 세팅과 OSV 사전 검증

> 6주차 · 문서 체계와 작업 규칙을 세우고, OSV PyPI 덤프로 "LLM이 근거로 삼을 수정 커밋이 얼마나 있는가"를 쟀다.
> 미리 정한 기준으로는 10.8%로 "범위 조정"이었다. 원인은 GHSA의 링크 표기 방식이었고, 근거 출처를 넓혀 53.3%로 조정했다(D-003).

---

## 요약

- 저장소에 문서 체계를 세웠다: 규칙(CLAUDE.md) / 갱신(프로젝트·현황) / 누적(decisions·기록·실습일지), `/기록`·`/실습일지` 스킬
- OSV PyPI 덤프(26,126개)를 받아 집계했다. **절반 가까이(45%)가 악성 패키지(MAL)**였고, 같은 취약점이 여러 ID로 중복돼 있어 묶으니 고유 취약점은 6,718건
- **측정 전에 판정 기준을 정했다.** FIX 링크와 GIT range 기준 최근 2년 후보는 **10.8% → "범위 조정"**
- 원인은 **GHSA가 수정 커밋을 전부 WEB 타입으로 붙이는 것**이었다. 대조해 보니 WEB 커밋의 99.8%가 실제 수정 커밋과 일치 → 근거 출처를 넓혀 **후보 53.3%** (D-003)
- 취약 함수를 구조화 필드에 넣은 항목은 **2건뿐** — LLM을 쓰는 전제를 데이터로 확인. 정답 후보 20건을 `eval/candidates.csv`로 뽑았다

## 배경 — 계획의 첫 전제를 데이터로 확인해야 했다

이 프로젝트는 LLM이 공개 취약점 문서(설명문 + 수정 커밋 diff)를 읽고 취약 함수를 뽑는다는 전제 위에 있다.
근거 문서가 대부분의 취약점에 없다면 LLM 단계 자체가 소수에만 적용된다.
그래서 6주차 최우선으로 `현황.md` 미확인 리스크 첫 항목 — "OSV PyPI 항목 중 FIX 커밋 비율" — 을 수치로 확인했다.

결과를 보고 기준을 맞추지 않도록, **판정 기준을 측정 전에 `현황.md`에 먼저 적었다.**

| 최근 2년 분석 가능 후보 비율 | 판정 |
|---|---|
| 50% 이상 | 계획대로 |
| 25~50% | 계획 유지 + 판단 불가 비율을 따로 보고 |
| 25% 미만 | 범위 조정 (decisions) |

분석 가능 후보 = GitHub 커밋 diff를 얻을 수 있음(FIX 링크 또는 GIT range) + details 200자 이상.
경계값은 데이터가 아니라 판단이다(근거는 `현황.md` §3).

## 한 일

### 1. 문서 체계와 작업 규칙

다른 프로젝트(26_2_AICapstone)의 문서 분리 방식과 기록 스킬을 참고해 이 프로젝트에 맞게 만들었다.

- `CLAUDE.md`: 매 세션 규칙만. 설계 원칙("판단은 코드, 해석은 LLM"), 판정 등급, 보안·비용 원칙, 의사결정 기록 기준
- `docs/프로젝트.md`(무엇을 왜) · `docs/현황.md`(지금 상태, 검증된 사실) · `docs/decisions.md`(계획을 바꾼 결정)
- `docs/decisions.md`에 기획 단계 결정 둘을 형식 본보기로 채웠다 — D-001(차별점 재설정), D-002(서비스가 API 비용 부담). 근거는 노션 주제 페이지
- `/기록`, `/실습일지` 스킬. 실습일지는 일지 번호와 작업 주차가 한 칸 어긋나므로 재료를 **날짜 범위**로 고르게 했다
- 실습일지 양식: 1학기 양식에서 내용과 그림을 지우고 제목을 "2026 심화응용프로젝트 실습일지"로 바꿨다(학번·이름이 있어 git 제외)

### 2. 공식 문서로 덤프와 스키마 확인

추측하지 않고 공식 문서부터 봤다.
- 덤프: [osv.dev/data](https://google.github.io/osv.dev/data/) — `storage.googleapis.com/osv-vulnerabilities/PyPI/all.zip`. HEAD 요청 결과 35.7MB, 당일 04:02 GMT 갱신
- 스키마: [osv-schema](https://ossf.github.io/osv-schema/) v1.9.1 — `aliases`는 "같은 취약점"이고 대칭·추이적. `withdrawn`이 있으면 철회. `MAL`은 악성 패키지 DB. `ecosystem_specific`·`database_specific`은 "DB가 정의, 평가에 영향 없음"

### 3. 덤프 표본 3개를 먼저 열어봄

본 집계 전에 PYSEC·GHSA·MAL 하나씩 열었다(`--peek 3`). 필드 구성은 문서와 같았지만 예상과 다른 점이 둘 있었다.

- **`PYSEC-2026-999`의 tensorflow 수정 커밋이 `FIX`가 아니라 `WEB` 타입이었다.**
  FIX와 GIT range만 세면 이런 건이 빠진다
- 같은 항목이 **2023년 CVE인데 published가 2026-07-07**이었다. PYSEC 재수입으로 보인다.
  "최근 2년"을 published로 자르면 옛 취약점이 섞일 수 있다

첫째는 판정 기준과 직결됐다. 비율을 보기 전이었으므로 사용자와 정했다:
**WEB 타입 커밋은 참고 행으로만 표시하고 판정은 원래 기준으로 한다. 두 기준의 판정이 갈리면 decisions에 남긴다.**
이 추가 규칙도 집계 전에 `현황.md`에 적었다.

### 4. 집계 — `scripts/analyze_osv.py`

- 덤프를 `data/raw/`에 캐시하고, 다운로드 시각과 Last-Modified를 메타 파일에 저장해 결과에 "스냅샷"으로 표시
- withdrawn·MAL을 분리하고, id와 aliases를 union-find로 묶어 고유 취약점 단위로 셌다.
  덤프에 없는 CVE ID도 다리 역할을 하도록 노드로 넣었다. 묶음 안에서 한 항목이라도 근거가 있으면 "있음"
- MAL과 alias로 이어진 일반 항목 묶음 41건도 악성 패키지로 보고 뺐다
- 최근 2년은 묶음 안 가장 이른 published 기준. 재수입 항목이 GHSA와 묶이면 GHSA 날짜가 쓰여 바로잡힌다

### 5. 판정이 갈렸다 → 원인 추적

결과: **원래 기준 10.8% → 범위 조정 / WEB 포함 53.3% → 계획대로.**

WEB 커밋을 근거로 써도 되는지 두 가지를 확인했다(`--web-check`).

1. **누가 WEB으로 붙이나** — GHSA는 GitHub 커밋 링크 5,261개가 전부 FIX가 아닌 타입이다. FIX를 쓰는 곳은 PYSEC뿐(2,163개).
   즉 "FIX 비율"은 사실상 PYSEC가 FIX로 분류해 준 비율이었다
2. **WEB 커밋이 실제 수정 커밋인가** — FIX·GIT 커밋과 WEB 커밋이 함께 있는 묶음 1,241건에서 대조했다.
   99.8%에서 WEB 커밋이 수정 커밋과 일치했고, 93.0%는 WEB 커밋 전부가 수정 커밋 목록에 있었다

사용자와 정한 조정: **WEB 타입 GitHub 커밋도 수정 커밋 근거로 인정한다**(D-003).
측정 전 기준은 고치지 않았다. 공식 판정은 "범위 조정"이고, 그 조정 내용이 근거 출처 확대다.
근거가 없는 나머지는 원안대로 "판단 불가 + 업데이트 권장".

검토했지만 택하지 않은 쪽:
- 원안 유지(FIX+GIT만) — 최근 2년의 11%만 정밀 판정. 차별점이 소수에만 적용
- details만으로 추출 — diff 교차 확인이 없어 "판단 불가"가 "여유 있음"으로 바뀔 위험. 위험 누락 0 원칙과 충돌

### 6. 정답 후보 20건 — `eval/candidates.csv`

- D-003 결정을 따라 WEB 포함 후보 풀(최근 2년)에서, 패키지가 겹치지 않게 20건(시드 20261008)
- 평가 세트가 서비스가 실제로 받을 입력과 같아야 정확도 수치가 의미를 가진다는 이유. FIX만 쓰면 PYSEC가 손질한 항목으로 치우친다
- `fix_commit_url`에 출처를 붙였다(`WEB https://…`). 20건 중 WEB 18, FIX 2
- 정답 세 칸은 비워 뒀고, 파일이 있으면 스크립트가 덮어쓰지 않는다. 작성 규칙은 `eval/README.md`(사용자와 확정)
- 정답을 직접 채우는 일은 7주차로 넘겼다

### 정규식(`xxx.yyy(`)의 한계

`[A-Za-z_]\w*(?:\.[A-Za-z_]\w*)+\(` — 점으로 이어진 이름 바로 뒤에 `(`.
- 놓치는 것: 점 없는 이름(`format()`), 괄호 없이 쓴 이름(`` `sqlparse.format` ``), 백틱 안 공백(`format (`)
- 잘못 잡는 것: 취약 함수가 아닌 예시 코드(`tf.raw_ops.RandomShuffle(` 재현 코드, `os.path.join(` 등)
- 그래서 41.7%는 "details에 코드 이름이 나오는 비율"의 대략적인 감일 뿐, 함수를 특정할 수 있는 비율이 아니다

## 남은 문제

- **WEB 커밋만 있는 취약점에서도 그 커밋이 수정 커밋인가** — 일치율은 PYSEC가 FIX를 단 묶음에서 잰 것이다.
  7주차 정답 작성 때 후보의 WEB 출처 18건을 확인해 note에 남긴다
- 한 묶음에 WEB 커밋이 여럿이면 수정 커밋이 아닌 것이 섞일 수 있다(약 7% 묶음). LLM에 넘기기 전 거르는 방법은 9주차 설계 때
- 신규 취약점이 2026년 들어 월 300건 안팎으로 늘었다. 이 건수의 실제 비용은 9주차 호출 단가 실측 후 판단
- 실행 환경: 이 PC에 Python 3.12가 없어 3.14로 돌렸다. 코드는 3.12 문법 범위로 썼다
- GitHub API 비인증 한도가 시간당 60회다(`--candidates` 1회에 10회 사용, 캡처용 재실행 후 잔여 40).
  앞으로 diff를 자주 받으므로 토큰 인증을 붙이기로 했다(공개 저장소 읽기 전용 토큰, `.env`)
- 6주차 실습일지는 이 기록을 재료로 작성해 당일 제출했다
